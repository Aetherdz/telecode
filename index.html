01 / The loop

One owner.
One clear route.

01

Connect your bot

Install locally and set the owner chat ID. The listener accepts only your configured chat.

02

Choose a session

Pick a named OpenCode session. Messages are routed to that target; attachments stay tied to the session selected when received.

03

Keep working

Send requests from Telegram. The agent can send text and allowlisted files back through MCP.

02 / Capabilities

Purpose-built, not a remote shell.

A

Named session routing

Browse sessions by title, page through the list, and switch the active target explicitly.

B

Model selection

Browse providers and models in Telegram. A selection updates the active OpenCode session.

C

File exchange

Route incoming attachments to their captured session and restrict outbound files to approved roots.

D

MCP replies

Local coding-agent clients can use bridge tools to send text, files, and session status.

E

Owner checks

The listener verifies the configured chat, with sender validation where Telegram provides a sender identity.

F

Local operation

No public webhook or hosted broker. Optional systemd user service starts the local listener.

06 / Security model

Keep control
on your machine.

Read the security notes ↗
  • Owner chat ID is checked before message routing.
  • Credentials are stored in a private runtime config, not the repository.
  • Outbound files are constrained by allowlisted roots and a deny list.
  • Session identifiers are validated before API calls.
  • Local listener lock prevents duplicate pollers.
  • Targeted routing is OpenCode-specific; MCP availability is not remote shell access.
